## Missing Migrations Needed

**None required for core logic.** The existing schema fully supports Phase 2.

One **optional migration** is recommended: add `warn_only` and `casual_before_regular_warning` config columns to `leave_types` to make the configurable-warning behaviour declarative. However, since the spec says these are configurable and the LeaveType already has all needed fields, these flags can be stored in `config/leave.php` as a simple array keyed by leave-type code. This avoids a migration and keeps Phase 2 self-contained.

- [ ] 3. Create `app/Services/LeaveBalanceService.php`
      All methods run inside `DB::transaction()`. The `leave_balances` row is fetched with `lockForUpdate()` before any mutation. Every mutation writes a `LeaveBalanceTransaction` row **first**, then updates `leave_balances.used` (or `entitled`/`carried_over` for accrual/carry-over).

      **Exact signatures:**
      ```php
      public function getOrCreateBalance(
          Employee $employee,
          LeaveType $leaveType,
          int $year
      ): LeaveBalance
      ```
      Uses `firstOrCreate(['employee_id' => ..., 'leave_type_id' => ..., 'year' => $year], ['entitled' => 0, 'carried_over' => 0, 'used' => 0])`. If creating for a `regular` leave type AND employee has an `entitlement_grade`, sets `entitled` = `$employee->regularLeaveEntitlement()`. For other leave types, sets `entitled` = `$leaveType->yearly_entitlement`.

      ```php
      public function deduct(
          LeaveBalance $balance,
          float $days,
          LeaveRequest $request,
          User $actedBy
      ): LeaveBalanceTransaction
      ```
      Inserts transaction `type=deduction, days=$days, leave_request_id=$request->id, created_by=$actedBy->id`. Then: `$balance->increment('used', $days)`. Returns the transaction.

      ```php
      public function refund(
          LeaveBalance $balance,
          float $days,
          LeaveRequest $request,
          User $actedBy
      ): LeaveBalanceTransaction
      ```
      Inserts transaction `type=refund, days=$days, leave_request_id=$request->id`. Then: `$balance->decrement('used', $days)` (floor at 0 using `max(0, $balance->used - $days)`). Returns transaction.

      ```php
      public function adjust(
          LeaveBalance $balance,
          float $days,
          string $note,
          User $actedBy
      ): LeaveBalanceTransaction
      ```
      `$days` may be positive or negative. Inserts transaction `type=adjustment`. Updates `entitled` if positive (adds to pool); updates `used` if negative adjustment (reduces used). Decision rule: if `$days > 0` → `$balance->increment('entitled', $days)`; if `$days < 0` → `$balance->decrement('used', abs($days))`. This keeps `remaining` correctly computed.

      ```php
      public function carryOver(
          Employee $employee,
          int $fromYear,
          int $toYear
      ): void
      ```
      For each `LeaveBalance` of `$employee` in `$fromYear` where `leaveType->deducts_balance = true` AND remaining > 0:
      - Compute `$carryDays = min($balance->remaining, config('leave.carry_over_max_days') ?? PHP_INT_MAX)`
      - Call `getOrCreateBalance($employee, $leaveType, $toYear)` with lock
      - Insert transaction `type=carryover, days=$carryDays` on the **toYear** balance
      - `$toBalance->increment('carried_over', $carryDays)`

      ```php
      public function accrueAnnual(
          Employee $employee,
          int $year
      ): void
      ```
      Iterates every active `LeaveType` where `yearly_entitlement > 0`. For `regular` type uses `$employee->regularLeaveEntitlement()`. Calls `getOrCreateBalance()`, then inserts transaction `type=accrual` and sets `entitled` to the computed value (replaces, not adds, since this is the annual reset). Uses `$balance->update(['entitled' => $days])` and appends the accrual transaction.

      Files: `app/Services/LeaveBalanceService.php`
      Verify: `./vendor/bin/pest tests/Feature/Phase2ServicesTest.php --no-coverage --filter balance` — balance service tests pass.

- [ ] 4. Create the five validation rules in `app/Rules/Leave/`

      **4a. `WorkingDaysRule`** — implements `ValidationRule`.
      Constructor: `__construct(private int $employeeOrganizationId)`.
      `validate(string $attribute, mixed $value, Closure $fail)`: receives the full request data via `setData()`. Reads `start_date` and `end_date` from `$this->data`. Iterates each day in the range using `CarbonPeriod::create($start, $end)`. Skips days where `Carbon::dayOfWeek` is in `config('leave.working_week_off_days')` (5=Fri, 6=Sat). Also queries `holidays` table for dates between start and end (`Holiday::whereBetween('date', [$start, $end])->pluck('date')`). Counts remaining days. If `$calculatedDays !== (float)$data['days']`, **does not call `$fail`** — instead sets `$this->calculatedDays` property. The rule is used to correct `days` on the request, not to reject. The `LeaveRequestService::create()` reads `$rule->calculatedDays` after validation and overwrites `$data['days']` before saving.

      **4b. `SufficientBalanceRule`** — implements `ValidationRule`.
      Constructor: `__construct(private Employee $employee, private LeaveType $leaveType, private int $year)`.
      Reads `config('leave.warn_only_insufficient_balance')`. If the balance's `remaining` < `$value` (days requested):
      - If `warn_only = true`: does NOT call `$fail`. Instead sets `$this->warning = "رصيدك المتبقي ({$remaining} يوم) أقل من المطلوب ({$value} يوم). سيستمر الطلب."` — caller reads `$rule->warning`.
      - If `warn_only = false`: calls `$fail("رصيد الإجازة غير كافٍ ...")`.

      **4c. `NoOverlapRule`** — implements `ValidationRule`.
      Constructor: `__construct(private int $employeeId, private ?int $excludeRequestId = null)`.
      Uses `LeaveRequest::overlapping($employeeId, $startDate, $endDate, $excludeRequestId)->exists()`. The `overlapping` scope already excludes rejected/cancelled. If exists → `$fail("يوجد طلب إجازة آخر يتداخل مع هذه الفترة.")`.

      **4d. `MaxDaysPerRequestRule`** — implements `ValidationRule`.
      Constructor: `__construct(private LeaveType $leaveType)`.
      If `$leaveType->max_days_per_request !== null` AND `$value > $leaveType->max_days_per_request` → `$fail("الحد الأقصى لهذا النوع من الإجازات هو {$leaveType->max_days_per_request} يوم في الطلب الواحد.")`.

      **4e. `CasualBeforeRegularRule`** — implements `ValidationRule`.
      Constructor: `__construct(private Employee $employee, private LeaveType $requestedType, private int $year)`.
      Only triggers when `$requestedType->code === 'regular'` AND `$value <= 2` (days). Checks if `casual` leave type exists and `$employee->balanceFor(casualId, $year)?->remaining > 0`. If so, and `config('leave.casual_before_regular_warning') = true`: sets `$this->warning = "ينبغي استخدام رصيد الإجازة العارضة أولاً قبل الاعتيادية للطلبات القصيرة."`. Never calls `$fail`.

      Files: `app/Rules/Leave/WorkingDaysRule.php`, `SufficientBalanceRule.php`, `NoOverlapRule.php`, `MaxDaysPerRequestRule.php`, `CasualBeforeRegularRule.php`
      Verify: `./vendor/bin/pest tests/Feature/Phase2ServicesTest.php --no-coverage --filter rules` — validation rule tests pass.

- [ ] 5. Create `app/Services/LeaveRequestService.php`

      Inject `LeaveBalanceService $balanceService` via constructor.

      **`create(array $data, User $createdBy): LeaveRequest`**
      - Instantiate and run `WorkingDaysRule`, `SufficientBalanceRule`, `NoOverlapRule`, `MaxDaysPerRequestRule`, `CasualBeforeRegularRule`.
      - Override `$data['days']` with `$workingDaysRule->calculatedDays`.
      - Collect any warnings from balance/casual rules into a `$warnings` array — stored on `$request->warnings` (a **non-persisted** property, set via `$request->setRelation('warnings', collect($warnings))`— or simply return a DTO; see note below).
      - Wrap in `DB::transaction()`: `LeaveRequest::create([...$data, 'created_by' => $createdBy->id, 'organization_id' => $createdBy->organization_id, 'status' => LeaveStatus::DRAFT])`.
      - Returns the created `LeaveRequest`.
      
      > **Note on warnings**: warnings are transient — they inform the UI but do not block. The service returns a simple value object `CreateResult(LeaveRequest $request, array $warnings)`. Define `app/Services/DTO/CreateLeaveRequestResult.php` as a `readonly class { public function __construct(public readonly LeaveRequest $request, public readonly array $warnings) {} }`.

      **`submit(LeaveRequest $request, User $submittedBy): LeaveRequest`**
      - Guard: `$request->status` must be `DRAFT` or `RETURNED` — else throw `LeaveRequestException::invalidTransition(...)`.
      - Inside `DB::transaction()`:
        1. Load the employee's current year balance for this leave type.
        2. Snapshot balance onto request: set `balance_entitled`, `balance_used`, `balance_remaining` from `$balance->entitled`, `$balance->used`, `$balance->remaining`. These never change after this point.
        3. Create `LeaveRequestStep` rows from `WorkflowConfiguration` for `$request->organization_id`, ordered by `step_order`, `is_active = true`. Each step: `['leave_request_id' => ..., 'step_order' => $wc->step_order, 'stage' => $wc->stage_name, 'status' => StepStatus::PENDING]`.
        4. Set `$request->status = LeaveStatus::SUBMITTED`, `$request->current_stage = first active step's stage_name`.
        5. `$request->save()` — observer stamps `submitted_at`.
        6. Dispatch notification to the first stage approvers (via `LeaveRequestNotification`).
      - Returns `$request->fresh()`.

      **`approve(LeaveRequest $request, LeaveRequestStep $step, User $actedBy, ?string $note): LeaveRequest`**
      - Guard: `$request->status` must be `IN_REVIEW` or `SUBMITTED`; `$step->status` must be `PENDING`; `$step->stage === $request->current_stage`. Throw `LeaveRequestException` otherwise.
      - Inside `DB::transaction()`:
        1. Update step: `status = APPROVED`, `acted_by = $actedBy->id`, `acted_at = now()`, `note = $note`.
        2. **Stage advancement logic** (ApprovalRule evaluation):
           - Load all steps with same `stage` (same `step_order` group) for this request.
           - Count total steps in this stage and how many are now `APPROVED`.
           - Get the `WorkflowConfiguration` for `$request->organization_id` and `stage_name = $step->stage` to read its `approval_rule`.
           - Call `$approvalRule->isStageApproved($approvedCount, $totalInStage)`.
           - **If stage IS approved**:
             - Mark any remaining `PENDING` steps in this stage as `SKIPPED`.
             - Find the next active `WorkflowConfiguration` step (higher `step_order`, `is_active = true`).
             - If next step exists: set `$request->current_stage = next->stage_name`, `$request->status = LeaveStatus::IN_REVIEW`. Create the next `LeaveRequestStep` row (if not already there). Dispatch notification to next stage.
             - If no next step (final approval reached): 
               - `$request->status = LeaveStatus::APPROVED`, `$request->current_stage = null`, `$request->decided_by = $actedBy->id`.
               - Call `$this->balanceService->deduct($balance, $request->days, $request, $actedBy)` — **only deduct on final APPROVED** and only if `$request->leaveType->deducts_balance = true`.
               - Dispatch approval notification to employee.
           - **If stage NOT yet approved**: just save the step — no request status change.
        3. `$request->save()`.
      - Returns `$request->fresh()`.

      **`reject(LeaveRequest $request, LeaveRequestStep $step, User $actedBy, string $reason): LeaveRequest`**
      - Guard: same as approve.
      - Inside `DB::transaction()`:
        1. Update step: `status = REJECTED`, note = `$reason`.
        2. Mark all other `PENDING` steps across all remaining stages as `SKIPPED`.
        3. `$request->status = LeaveStatus::REJECTED`, `$request->rejection_reason = $reason`, `$request->current_stage = null`, `$request->decided_by = $actedBy->id`.
        4. `$request->save()`.
        5. Dispatch rejection notification to employee.
      - Returns `$request->fresh()`.

      **`return(LeaveRequest $request, LeaveRequestStep $step, User $actedBy, string $note): LeaveRequest`**
      - Guard: status must be `SUBMITTED` or `IN_REVIEW`; step must be `PENDING`.
      - Inside `DB::transaction()`:
        1. Update step: `status = RETURNED`, `note = $note`.
        2. Mark all other `PENDING` steps as `SKIPPED`.
        3. `$request->status = LeaveStatus::RETURNED`, `$request->current_stage = null`.
        4. `$request->save()`.
        5. Dispatch "return for correction" notification.
      - Returns `$request->fresh()`.

      **`cancel(LeaveRequest $request, User $cancelledBy): LeaveRequest`**
      - Guard: `$request->status->canBeCancelled()` must be true.
      - Inside `DB::transaction()`:
        1. `$request->status = LeaveStatus::CANCELLED`, `$request->current_stage = null`.
        2. If the request was previously `APPROVED` (cancelling after approval): call `$this->balanceService->refund(...)`.
        3. Mark all `PENDING` steps as `SKIPPED`.
        4. `$request->save()`.
      - Returns `$request->fresh()`.

## Step Advancement Decision Table

```
Stage action    ApprovalRule    Condition                          → Request transition
─────────────────────────────────────────────────────────────────────────────────────
approve step    ANY             approvedCount >= 1                 advance to next stage (or APPROVED)
approve step    ALL             approvedCount == totalInStage      advance to next stage (or APPROVED)
approve step    ALL             approvedCount < totalInStage       no change (wait for others)
approve step    MAJORITY        approvedCount > totalInStage / 2   advance to next stage (or APPROVED)
approve step    MAJORITY        approvedCount ≤ totalInStage / 2  no change
reject step     any             immediate                          REJECTED, skip all pending
return step     any             immediate                          RETURNED, skip all pending
```

When advancing to next stage, new `LeaveRequestStep` rows are created for each approver implied by the next `WorkflowConfiguration` entry. Since `workflow_configurations` defines one row per stage (not per approver), a single step row is created per stage. This matches the existing schema: `unique(leave_request_id, step_order)`.

## Notes and Assumptions

1. **Balance deduction timing**: deducted only on final APPROVED, not when submitted. Refunded on cancel (if previously approved) or reject (no deduction had happened, so no refund needed).
2. **Urgency requests without balance deduction**: the `leave_types.deducts_balance = false` flag already covers this. Administration-created urgent requests go through the same service with the same `deducts_balance` check.
3. **Admin creating requests on behalf of an employee**: `LeaveRequestService::create()` receives `$createdBy` which may be an admin user — the `employee_id` in `$data` is the actual employee. `organization_id` is taken from `$employee->organization_id`, not from `$createdBy`.
4. **Race conditions on balance**: `lockForUpdate()` inside `DB::transaction()` in `LeaveBalanceService` is the sole protection. The `LeaveBalanceObserver` warning is left in place as an additional guard but will never fire if all mutations go through the service.
5. **Pre-existing failing test**: `Phase1FoundationTest` has one known failure ("null grade defaults to 28") caused by the factory generating `birth_date` > 50 years ago. This is a Phase 1 factory issue, unrelated to Phase 2 — do not fix it here.
