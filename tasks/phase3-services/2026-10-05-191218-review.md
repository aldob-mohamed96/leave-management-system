# Phase 3 — Filament Admin Panel: Full Implementation Review

The Phase 3 implementation wires a Filament 3.x admin panel onto an existing Laravel 11 leave-management backend. It bootstraps the panel with Arabic locale and branding, adds `FilamentUser` to the User model, creates four policies (Organization, User, Employee, LeaveRequest), and builds six Filament resources (Organization, User, Employee, LeaveType, Holiday, LeaveRequest). The most complex piece — LeaveRequestResource — integrates with `LeaveRequestService` for create/submit/approve/reject/return/cancel and scopes its query by the authenticated user's permission level.

**Watch for:** `submit` action gates on `can('create')` instead of `submit_leave_request` — confirmed permission mismatch. Arabic locale is handled correctly via `.env`/`config/app.php` rather than a non-existent Filament v3 `Panel::locale()` method.

**Verdict**: NEEDS_CHANGES

---

## High-level view

The panel bootstrap (AdminPanelProvider) passes all criteria: `Color::Blue`, `brandName`, Tajawal font via `GoogleFontProvider`, and four navigation groups with the correct Arabic labels and icons. `->locale('ar')` is not present on the panel — correctly omitted because Filament v3.3.56 does not have that method — and Arabic locale is set via `APP_LOCALE=ar` in `.env`, which is the right approach.

The User model implements `FilamentUser`, and `canAccessPanel` correctly calls `setOrganizationTeam()` before all role/permission checks. All four policies follow the same pattern: `setOrganizationTeam()` first, then `hasPermissionTo()`. AppServiceProvider registers them via `Gate::policy()` in a clean `$policies` loop.

The five catalog resources (Organization, User, Employee, LeaveType, Holiday) match their specs for columns, form fields, filters, and navigation group/icon/label. BalanceBadge renders at `filament.columns.balance-badge` via `ViewColumn` with the correct Blade view. LeaveType and Holiday use static `canViewAny/canCreate/canEdit/canDelete` guards against `manage_organization` rather than a separate policy class, which matches the spec.

LeaveRequestResource's `getEloquentQuery()` correctly branches on `view_all_leave_requests` (scopes to `subtreeIds()`) vs `view_leave_requests` (scopes to own org). `CreateLeaveRequest::handleRecordCreation()` delegates to `LeaveRequestService::create()`. `EditLeaveRequest::handleRecordUpdate()` patches only the allowed fields directly (never re-invokes the service), with `authorizeAccess()` checking both the policy gate and `canBeEdited()`.

The one blocking issue: the Submit action's `visible` guard uses `can('create', LeaveRequest::class)` (mapping to `create_leave_request`), not the `submit_leave_request` permission. These are distinct in the seeder and assigned to different role sets, so a user with `submit_leave_request` but not `create_leave_request` will see the button suppressed. The LeaveRequestPolicy has no `submit` method, so there is no proper gate to call.

### Submit visibility gates on `create_leave_request` instead of `submit_leave_request`

In `LeaveRequestResource.php` (table action) and `ViewLeaveRequest.php` (header action), the Submit action's `visible` closure checks:

```php
Auth::user()?->can('create', LeaveRequest::class)
```

`LeaveRequestPolicy::create()` checks `create_leave_request`. The seeder defines `submit_leave_request` as a distinct permission, assigned to all roles that include submission rights. A role holder who has `submit_leave_request` but not `create_leave_request` — which is a plausible setup when only admins can create requests on behalf of others — will never see the submit button. The policy has no `submit` method, so no clean gate exists to use.

The fix is two parts:

1. Add to `LeaveRequestPolicy`:
```php
public function submit(User $user, LeaveRequest $leaveRequest): bool
{
    $user->setOrganizationTeam();
    return $user->hasPermissionTo('submit_leave_request');
}
```

2. Update both Submit action `visible` closures from `can('create', LeaveRequest::class)` to `can('submit', $record)`.

This is the only blocking finding. All 95 existing tests pass; all routes are registered; all other criteria are satisfied.

</details>
