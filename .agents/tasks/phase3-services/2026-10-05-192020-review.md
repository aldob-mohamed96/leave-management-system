# Phase 3 Filament Admin Panel — Leave Management System

This change delivers the full Filament 3.x admin panel for the Luxor Directorate leave management system. It wires five catalog resources (Organization, User, Employee, LeaveType, Holiday), a complex LeaveRequestResource that integrates the existing `LeaveRequestService` workflow, the `BalanceBadge` component, all four authorization policies, and the AdminPanelProvider configuration. The foundation pattern is consistent throughout: every policy calls `setOrganizationTeam()` before any Spatie permission check, and every service call is wrapped in try/catch with a `Notification::make()->danger()` fallback. Arabic locale is delivered via `APP_LOCALE=ar` in `.env` rather than a panel method, which is the correct approach for Filament v3 (confirmed in FEAT-001 findings).

**Watch for:** `confirmed` — The `BalanceBadge` ViewColumn references Blade view `filament.columns.balance-badge`, which resolves to `resources/views/filament/columns/balance-badge.blade.php`; a second file at `resources/views/filament/components/balance-badge.blade.php` is unused by the column and causes no bug but is dead code. `confirmed` — `EditLeaveRequest` applies `handleRecordUpdate()` for both DRAFT and RETURNED status using direct `$record->update()` — it does not call `LeaveRequestService::create()` for DRAFT edits, which means the validation rules (overlap, max days, balance check) are bypassed when editing a draft. `possible` — The navigation badge in `LeaveRequestResource::getNavigationBadge()` calls `LeaveRequest::withoutGlobalScopes()->pending()->count()` without scoping to the user's organization, so privileged users may see an inflated count.

**Verdict**: NEEDS_CHANGES

## High-level view

The AdminPanelProvider is correctly configured: `Color::Blue`, brand name in Arabic, Tajawal via `GoogleFontProvider`, four navigation groups with the correct Arabic labels and Heroicon icons. The `->locale('ar')` call from the spec was intentionally dropped because Filament v3 does not support it; Arabic is set application-wide via `APP_LOCALE=ar` in `.env`, which is the right place for this.

All four policies call `setOrganizationTeam()` before any permission check and cover every permission the spec required. Policy registration in `AppServiceProvider` uses the `$policies` array loop with `Gate::policy()`. `LeaveTypeResource` and `HolidayResource` use static `Gate::allows('manage_organization')` overrides instead of a separate Policy class, matching the spec.

`LeaveRequestResource` covers all nine table columns, all four filters including the date-range filter, and all five workflow actions on both the list table and the View page. Each action fetches the pending step, guards against a missing step, calls the correct `LeaveRequestService` method, and catches both `LeaveRequestException` and `ValidationException`. The `getEloquentQuery()` override forks between `view_all_leave_requests` (subtree scope) and `view_leave_requests` (own org only), but `getNavigationBadge()` runs the same `withoutGlobalScopes()->pending()->count()` query with no user context — a lower-privilege user sees the directorate-wide pending count in the sidebar badge.

`CreateLeaveRequest` delegates to `LeaveRequestService::create()`, enforcing all five validation rules. `EditLeaveRequest` enforces the policy gate and `canBeEdited()` guard in `authorizeAccess()`, then patches fields directly via `$record->update()` — for both DRAFT and RETURNED status. For RETURNED that's intentional. For DRAFT it skips the overlap, max-days, and balance checks that the service would enforce, allowing invalid date combinations to be saved silently.

1. **Draft edit bypasses service validation** — `EditLeaveRequest::handleRecordUpdate()` calls `$record->update($updateData)` for both DRAFT and RETURNED status. RETURNED is intentional (spec says patch directly), but DRAFT should re-route through `LeaveRequestService::create()` (or a dedicated `update()` method) to re-run overlap, max-days, and balance checks. Fix: check `$record->status === LeaveStatus::DRAFT` in `handleRecordUpdate()` and call the service for that branch.

2. **Duplicate / dead BalanceBadge Blade view** — `resources/views/filament/components/balance-badge.blade.php` exists but is not referenced by the `ViewColumn` (which uses `filament.columns.balance-badge`). The PHP `BalanceBadge::render()` helper could use it, but nothing in production calls `BalanceBadge::render()` from the panel. Delete or consolidate to avoid future confusion.

3. **Navigation badge over-counts across organizations** — `getNavigationBadge()` calls `LeaveRequest::withoutGlobalScopes()->pending()->count()`, which returns the global pending count regardless of the logged-in user's organization scope. A `مسؤول الإجازات` at a single school sees the count for the entire directorate. Scope it to the same permission-aware query used in `getEloquentQuery()`.

### Draft edit bypasses LeaveRequestService validation

`EditLeaveRequest::handleRecordUpdate()` uses a single `$record->update($allowed)` path for both DRAFT and RETURNED status. The spec says RETURNED records should be patched directly (keeping status as RETURNED without re-running the service), which is correct. But DRAFT edits should go through `LeaveRequestService::create()` — or at least a `LeaveRequestService::update()` method — to re-enforce the no-overlap rule, the max-days-per-request rule, and the sufficient-balance check. As it stands, an admin can change a DRAFT's dates to overlap with another approved request and save without any error. **confirmed** — the `handleRecordUpdate()` body has no status branch; it always calls `$record->update()`.

### Navigation badge scoping gap

`getNavigationBadge()`:
```php
return (string) LeaveRequest::withoutGlobalScopes()->pending()->count() ?: null;
```
This runs with no user context. A lower-privilege user whose `getEloquentQuery()` scopes to their own organization sees an org-wide count in the badge. The fix is to replicate the permission fork from `getEloquentQuery()` or call `static::getEloquentQuery()->pending()->count()` directly. **confirmed** — the badge query does not apply any org filter.

### Dead BalanceBadge component view

Two Blade views exist for the balance badge: `resources/views/filament/columns/balance-badge.blade.php` (used by `ViewColumn` in `EmployeeResource`) and `resources/views/filament/components/balance-badge.blade.php` (not referenced from any Filament panel code). The `BalanceBadge::render()` static helper builds its own HTML string and does not render either view. The `filament/components/` file is unreachable dead code. **confirmed** — no `view('filament.components.balance-badge')` call exists anywhere in the codebase.

### Test coverage

All 95 existing tests pass. The new Filament layer has no Pest/Feature tests — no tests for policy `authorize` calls, no tests for the `EditLeaveRequest` DRAFT-edit path, and no tests for `getEloquentQuery()` permission branching. The most important gap is the DRAFT edit bypass described above, which would have been caught by a feature test that attempts to save overlapping dates on a DRAFT record and expects a validation error.
