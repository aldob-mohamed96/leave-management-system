# رصيد إجازات اعتيادية مُرحَّل — حقل الرصيد السابق

The change adds a create-only form field, `initial_balance_days`, that lets an administrator seed a legacy regular-leave balance for a newly created employee without touching the `employees` table schema. The value flows into `leave_balances.carried_over` for the current year via a `LeaveBalanceTransaction::ADJUSTMENT` entry, recorded inside a `DB::transaction` with a `lockForUpdate` guard. The plan deliberately skips `LeaveBalanceService::adjust()` because that method only touches `entitled` and `used`, not `carried_over`; the direct write is intentional and semantically correct.

Watch for: (1) **confirmed** — `TransactionType::ADJUSTMENT` does not satisfy `isCredit()`, so any reporting logic that sums credits will silently exclude legacy balance entries; (2) **confirmed** — `EditEmployee.afterSave()` was not extended; the review criteria required it but the plan explicitly argued against it — the conflict needs to be resolved; (3) **possible** — no log or notification when `LeaveType code='regular'` is missing, causing a silent no-op on the balance write.

**Verdict**: NEEDS_CHANGES

---

## High-level view

The form field is correctly placed — after `entitlement_grade`, before `user_id`, marked `->visibleOn('create')` and `->dehydrated(false)` — so it never leaks to the `employees` table and is invisible on the edit form. The data is captured in `mutateFormDataBeforeCreate()` via a property stash with a `max(0, …)` floor guard, and stripped from `$data` before the record is saved.

The `ADJUSTMENT` transaction type is used but returns `false` from `isCredit()` — it is neither credit nor debit in the type system. Any balance-summary or reporting code that totals credits via `isCredit()` will miss these entries. The `CARRYOVER` type was deliberately avoided to distinguish admin-seeded legacy data from automated year-end rollover, but that leaves `ADJUSTMENT` in an unclassified state. A dedicated enum case or an explicit documented convention is needed.

`EditEmployee.afterSave()` was intentionally left unchanged because the field is hidden on the edit form. The review criteria and the plan are in explicit conflict on this point; it needs a product decision before closing.

<details>
<summary>Issues (3)</summary>

1. **ADJUSTMENT not classified as credit** — `TransactionType::ADJUSTMENT` returns `false` for both `isCredit()` and `isDebit()`. Legacy balance days increase the employee's effective balance but will not appear in any reporting that sums credits. Either introduce a `LEGACY_CARRYOVER` case that returns `true` from `isCredit()`, or explicitly document that balance-summing queries must include `ADJUSTMENT` rows.

2. **afterSave not implemented in EditEmployee** — The review criteria required `EditEmployee.afterSave()` to apply the same additive adjustment. The implementation omits this by design (field is hidden on edit). If administrators ever need to add a legacy balance to an existing employee there is no UI path for it. Confirm with the product owner whether create-only seeding is the complete requirement.

3. **Silent no-op when `regular` LeaveType is missing** — If `LeaveType` with `code = 'regular'` does not exist, the entire block is skipped with no log and no user-facing notification. The admin receives a success toast but the balance is never applied. Add `Log::warning('initial_balance: regular leave type not found', ['employee_id' => $this->record->id])` at minimum, or surface a Filament warning notification so the gap is detectable.

</details>

<details>
<summary>Details</summary>

### `ADJUSTMENT` type and credit classification

`TransactionType` defines `isCredit()` as returning `true` only for `ACCRUAL`, `REFUND`, and `CARRYOVER`. `ADJUSTMENT` returns `false` from both, making it a neutral/uncategorized type. For this feature the transaction represents days that increase the employee's available balance — semantically a credit. If any part of the codebase sums credits to compute a balance view or report, legacy entries will be excluded. A dedicated enum case (`LEGACY_CARRYOVER`, classified as credit) would resolve this cleanly without changing the meaning of `ADJUSTMENT` for other uses.

### Silent skip when `regular` LeaveType is absent

The `if ($regularType)` guard prevents a crash but produces no observable signal. An administrator who enters 10 legacy days and clicks Save will receive Filament's standard success notification — the employee is created — but the carried-over balance is zero. `Log::warning` is the minimum fix; a `Notification::make()->warning()->title('لم يتم تطبيق الرصيد السابق: نوع الإجازة الاعتيادية غير موجود')->send()` inside the false branch would make the failure immediately visible.
